# 17 배포 운영 런북

> Mac 현재 운영은 수동 Compose다. GitHub CI/ARM 게시 workflow를 구현했으며 원격 검증과 비공개 Mac receiver 구성은 진행 중이다. 완료 여부는 [Step 04](../steps/step-04-github-actions-cicd.md)를 확인한다. 아래 수동/레거시 절차를 자동 CD와 연속 실행하지 않는다.

## 1. 구조와 준비

운영 Compose는 Nginx만 외부 공개하고 `/`·`/api`·`/ws`를 각각 frontend·backend에 proxy한다. `/docs`, `/openapi.json`, `/redoc`은 운영 Nginx에서 404다. 개발 Compose override는 8080 포트와 FastAPI 문서 proxy를 제공한다.

Mac은 project `smartdrain-mac`, PostgreSQL volume `smartdrain-mac_postgres_data`, nginx `127.0.0.1:8099`를 유지한다. 환경값은 추적 제외 `.env`, 모델은 host의 `best.pt`에서 공급한다. 운영 전용 경로는 `/Users/tro/apps/smartdrain`으로 준비했으며 기존 컨테이너의 bind 경로 전환은 아직 하지 않았다.

기존 VM Jenkinsfile은 `DEPLOY_DIR=/home/yp/apps/smart-drain`, 같은 custom workspace, Secret File을 `.env`로 복사하는 구조다. 이는 레거시 VM 설정이며 Mac CD에서 사용하지 않는다. 기존 VM Job의 활성 상태를 확인하기 전 제거하지 않는다.

## 2. 수동 Compose 실행 순서

1. `docker compose config --quiet`로 설정을 확인한다.
2. 모델 파일 경로와 읽기 권한을 확인한다.
3. Compose build·기동 시 `migrate`가 Alembic head를 적용한 뒤 backend를 기동하는지 확인한다.
4. 필요할 때만 `docker compose --profile seed run --rm seed`를 실행한다.
5. `docker compose ps`, Nginx `/`, backend health, REST, WebSocket을 smoke test한다.
6. 실패 시 `docker compose logs nginx backend ai-service migrate`를 먼저 수집한다.

## 3. 장애 대응 순서

| 증상 | 우선 확인 |
| --- | --- |
| Jenkins workspace/배포 경로 불일치 | Jenkinsfile의 `customWorkspace`, `DEPLOY_DIR`, checkout 위치 |
| `.env` 또는 DB 비밀번호 오류 | Secret File 복사 결과와 `COMPOSE_DATABASE_URL` |
| Nginx mount·port 오류 | `nginx/default.conf`, host port 점유, 컨테이너 logs |
| migration 실패 | migrate logs·DB health·Alembic revision |
| 모델 mount 실패 | `SMARTDRAIN_YOLO_MODEL_PATH`, 파일 크기·권한 |
| AI health만 성공 | 실제 샘플 분석과 callback을 별도 확인 |
| 이전 image/container 잔존 | `docker compose ps`와 image 목록 확인 후 계획된 정리 |

`docker compose down -v`, image prune, volume 정리는 데이터를 제거할 수 있으므로 운영에서는 별도 승인과 백업 뒤에만 수행한다. Cloudflare host Tunnel은 Health Center 공통 운영 세션이 관리한다. 이 CI/CD에서 route/DNS/Access를 변경하지 않는다.

## 4. GitHub Actions 구성과 현재 활성화 경계

| Workflow | Trigger | 역할 |
| --- | --- | --- |
| `ci.yml` | PR 대상 dev/main, reusable call, 수동 | Compose local/dev/digest 설정, Frontend lint/build, 빈 PG16 migration/API, AI pytest |
| `release.yml` | main push | CI 재사용 → 세 Linux/arm64 image build/push → release manifest → 조건부 private dispatch |
| `release.yml` 수동 실행 | workflow_dispatch | build-only. GHCR 게시·Mac 배포 없음 |

CI에는 운영 `.env`, 모델, dispatch secret을 전달하지 않는다. Frontend는 `packageManager`에 고정된 pnpm 12.5.1과 Node 22를 사용한다. AI pytest는 기존 requirements를 제약 파일로 읽어 ML image 없이 계약을 검사한다. 실제 추론은 별도 reference smoke가 담당한다.

### 초기 설정

- Repository secret `COMPOSE_FRONTEND_KAKAO_MAP_APP_KEY`: `Settings → Secrets and variables → Actions → Secrets → New repository secret`에 Kakao JavaScript 키를 등록한다. workflow는 `secrets`에서 읽어 Frontend build Job에만 전달하며 GitHub 자동 로그 마스킹과 기존 `add-mask` 처리를 사용한다. Variables에 같은 이름으로 등록해도 읽지 않는다. API는 same-origin으로 build한다.
- 이 Secret은 GitHub 저장·로그 노출을 줄이기 위한 것이다. 기존 Docker build argument와 `NEXT_PUBLIC_KAKAO_MAP_APP_KEY`로 전달되므로 빌드 산출물·브라우저의 지도 SDK 요청에서 키를 완전히 숨기지 않는다. Kakao JavaScript SDK 허용 도메인을 실제 서비스 도메인으로 제한하고 서버용 비밀키는 넣지 않는다.
- `SMARTDRAIN_AUTO_DEPLOY_ENABLED`: 첫 적용 검증 전에는 **미설정 또는 false**다. true는 private receiver·runner·권한과 첫 배포가 검증된 뒤에만 설정한다.
- public `release` environment: main만 허용하고 `SMARTDRAIN_DEPLOY_DISPATCH_TOKEN`을 보관한다. 권한은 private 운영 repo 하나의 Actions write로 제한한다.
- private receiver는 `yellow-pang/mac-mini-deploy`의 `deploy-smartdrain.yml`, ref main을 기준으로 준비한다. 아직 배포 가능 상태를 뜻하지 않는다.
- GHCR package Actions access, source artifact read 권한, runner 등록과 보호 규칙은 실제 설정 후 Steps에 기록한다.

main 최초 병합은 auto deploy를 끈 상태로 이미지 게시까지만 검증한다. 이후 같은 main run을 private receiver에서 검증하고 통제된 첫 배포를 수행한다. feature/dev 수동 build를 main 성공 release로 사용하지 않는다. 구체적인 Gate는 [Plan 04](../plans/plan-04-github-actions-cicd.md)를 따른다.

### 게시 결과와 재실행

배포는 `latest` 대신 `package@sha256:<digest>`를 사용한다. backend/migrate/seed는 동일 image reference를 공유한다. 공개 run 성공은 이미지 게시·전달 성공이며, 운영 성공은 private receiver 결과와 실제 실행 digest로 확인한다.

- 성공한 service build artifact: `digest-<service>-<run_id>`.
- 게시 manifest: `release-manifest-<run_id>`, 파일 `release-manifest.json`.
- source repo/SHA/run, image digest, service별 `build_attempts`, `manifest_attempt`를 기록한다.
- 실패 job만 재실행하면 같은 run/SHA의 성공 artifact를 재사용한다. 새 commit의 결과를 섞지 않는다.
- Secrets 전환처럼 workflow 파일을 수정했다면 수정 commit이 포함된 새 main Release를 사용한다. 과거 실행의 재시도는 과거 workflow revision을 사용한다. Secrets 참조가 이미 반영된 workflow에서 Secret 값만 등록·수정한 경우에는 실패 job 재실행을 사용할 수 있다.
- dispatch만 재시도할 때 AI를 다시 build하지 않는다. receiver는 `build_attempts ≤ manifest_attempt ≤ source_run_attempt`와 최신 source attempt의 최종 success를 확인해야 한다.
- artifact가 만료되면 재사용을 실패 처리한다. 누락된 image를 로컬에서 자동 build하거나 임의 tag로 대체하지 않는다.

### 실제 AI reference smoke

기존 `ai_service.scripts.smoke_analysis`에 `--verify-reference`를 지정하면 drain 2의 고정 sensor 입력, 승인된 모델/sample/XGBoost hash와 기대 분류를 검사한다. 세 hash 및 `--expected-yolo-status`, `--expected-risk-level`, `--expected-final-decision`을 모두 전달해야 한다. 실제 baseline은 Step 04의 기록을 사용하며 새 결과에 맞춰 자동 변경하지 않는다.

YOLO `unknown/-1/-1` sentinel은 실패다. XGBoost의 정상 `unknown/field_check`는 기준과 일치하면 성공이다. 이 smoke는 callback을 보내지 않으므로 운영 DB를 쓰지 않으며, callback→DB→WS 전체 E2E를 대신하지 않는다.
