# SmartDrain Documentation Policy

## 1. 문서 목적

이 문서는 SmartDrain 저장소의 문서 종류, 저장 위치, 파일 이름, 번호 체계와 작성 원칙을 정의합니다.

기존 문서 구조가 이미 있다면 기존 규칙을 우선합니다.

## 2. 문서 종류

SmartDrain 문서는 다음과 같이 구분합니다.

| 문서 종류    | 목적                       |
| ------------ | -------------------------- |
| README       | 프로젝트 소개와 실행 안내  |
| Reference    | 현재 구조와 공통 기준      |
| Plans        | 구현 전 조사와 작업 계획   |
| Steps        | 실제 구현 과정과 결과 기록 |
| PR           | 리뷰어용 변경 요약         |
| Legacy       | 기존 MVP 또는 과거 산출물  |
| Verification | 테스트와 운영 검증 기준    |

## 3. 기본 디렉터리

기존 규칙이 없으면 다음 구조를 사용합니다.

```text
docs/
├─ reference/
├─ plans/
├─ steps/
├─ pr/
├─ verification/
└─ legacy-mvp/
```

특정 서비스에만 해당하고 서비스별 문서 구조가 필요한 경우 다음처럼 구성할 수 있습니다.

```text
frontend/docs/
```

현재 저장소에는 `frontend/docs/`와 `ai_service/docs/`가 존재하지만 `backend/docs/`는 없습니다. 존재하지 않는 서비스 문서 디렉터리는 명확한 필요 없이 새로 만들지 않습니다.

전체 저장소에 영향을 주는 문서는 루트 `docs/` 아래에 작성합니다.

## 4. Plans 문서

Plans 문서는 실제 구현 전에 작성합니다.

목적:

- 현재 구현 조사
- 문제 정의
- 작업 범위 설정
- 구현 대안 비교
- 위험 확인
- 사용자 승인 획득

기본 위치:

```text
docs/plans/
```

기본 파일명:

```text
plan-<번호>-<작업명>.md
```

작은 오탈자, 한 파일의 단순 문서 교정, 동작을 바꾸지 않는 좁은 범위 수정은 Plans 문서를 생략할 수 있습니다.

## 5. Steps 문서

Steps 문서는 구현과 검증이 끝난 뒤 작성합니다.

목적:

- 실제 변경 기록
- 선택 이유 설명
- 파일별 역할 설명
- 검증 결과 기록
- Plans와 실제 구현 차이 기록

기본 위치:

```text
docs/steps/
```

기본 파일명:

```text
step-<번호>-<작업명>.md
```

Steps 문서는 기록 가치가 있는 작업에서 작성합니다. 작은 오탈자나 영향이 낮은 단순 수정은 생략할 수 있습니다.

## 6. PR 문서

PR 문서는 사용자가 명시적으로 요청한 경우 작성합니다.

목적:

- 리뷰어가 핵심 변경을 빠르게 파악
- 영향 범위 확인
- 검증 결과 확인
- 리뷰 요청 사항 전달

기본 위치:

```text
docs/pr/
```

기본 파일명:

```text
pr-<번호>-<작업명>.md
```

## 7. 번호와 이름 연결

하나의 작업에 속하는 Plans, Steps, PR 문서는 가능한 한 같은 번호와 작업명을 사용합니다.

예:

```text
docs/plans/plan-03-websocket-reconnection.md
docs/steps/step-03-websocket-reconnection.md
docs/pr/pr-03-websocket-reconnection.md
```

PR 문서에는 관련 Plans와 Steps 문서의 상대 경로를 포함합니다.

## 8. 파일 번호 선택

기존 번호 체계가 있으면 다음 번호를 이어서 사용합니다.

번호 충돌을 피하기 위해 문서 디렉터리의 기존 파일을 먼저 확인합니다.

번호 형식은 저장소의 기존 스타일을 우선합니다.

예:

```text
01
02
03
```

또는:

```text
001
002
003
```

두 형식을 같은 디렉터리에서 혼용하지 않습니다.

## 9. 파일 이름

파일 이름은 가능한 한 영어 kebab-case를 사용합니다.

예:

```text
plan-04-frontend-image-state-fix.md
step-04-frontend-image-state-fix.md
pr-04-frontend-image-state-fix.md
```

기존 저장소가 한글 파일명을 사용하고 있다면 기존 방식을 우선할 수 있습니다.

파일 이름만 보고 문서 목적을 알 수 있도록 작성합니다.

## 10. 문서 언어

문서는 기본적으로 한국어로 작성합니다.

다음 항목은 원문 표기를 유지할 수 있습니다.

- 코드
- 명령어
- 파일명
- 클래스명
- 함수명
- API endpoint
- 환경변수
- 공식 기술 용어

## 11. README 기준

루트 `README.md`는 다음 역할을 담당합니다.

- 프로젝트 소개
- 주요 기능
- 기술 스택
- 전체 실행 방법
- 아키텍처 개요
- 주요 문서 링크
- 포트폴리오 대표 문서

하위 README는 각 서비스 담당자가 해당 서비스를 실행하고 검증할 수 있는 운영 노트로 유지합니다.

오래된 실행 명령, 절대 로컬 경로, 현재 구조와 맞지 않는 내용을 발견하면 관련 작업 범위 안에서 갱신합니다.

## 12. Reference 문서

`docs/reference/`에는 자주 변경되지 않는 현재 기준을 작성합니다.

예:

- 저장소 구조
- 서비스 책임
- 문서 정책
- 코딩 규칙
- API 계약 기준
- 환경변수 정책
- 브랜치 정책

실제 작업 과정은 Reference가 아니라 Plans 또는 Steps에 작성합니다.

## 13. Legacy 문서

기존 MVP 산출물이나 현재 구현과 다른 과거 문서는 `legacy-mvp/` 등 별도 위치에 보관합니다.

Legacy 문서를 현재 기준처럼 사용하지 않습니다.

필요한 경우 문서 상단에 다음 내용을 표시합니다.

```markdown
> 이 문서는 기존 MVP 기준의 기록이며 현재 구현과 다를 수 있습니다.
```

## 14. 현재 구현과 향후 계획 구분

문서에서는 다음 상태를 구분합니다.

- 현재 구현됨
- 부분 구현
- 계획됨
- 검토 중
- 미구현
- 레거시

아직 구현하지 않은 기능을 현재 기능처럼 작성하지 않습니다.

## 15. Markdown 작성 원칙

- 제목 구조를 일관되게 사용합니다.
- 지나치게 긴 문단은 나눕니다.
- 파일과 명령어는 코드 형식으로 표시합니다.
- 비교가 필요한 경우 표를 사용합니다.
- 흐름 설명에는 Mermaid를 사용할 수 있습니다.
- 코드 전체보다 핵심 인터페이스와 흐름을 설명합니다.
- 동일한 내용을 여러 문서에 반복하지 않습니다.
- 반복이 필요한 경우 기준 문서 링크를 제공합니다.

## 16. Mermaid 사용

Mermaid는 다음 상황에 사용합니다.

- 서비스 간 흐름
- 요청과 응답 순서
- 상태 전환
- 배포 과정
- 데이터 처리 과정

실제 코드와 다른 이상적인 흐름을 현재 구조처럼 표시하지 않습니다.

## 17. 문서 갱신 기준

다음 변경이 발생하면 관련 문서를 확인합니다.

- 디렉터리 구조 변경
- 실행 명령 변경
- 환경변수 변경
- API 계약 변경
- DB schema 변경
- Docker 구성 변경
- CI/CD 변경
- 서비스 책임 변경

코드와 문서가 다르면 현재 구현을 기준으로 문서를 갱신하고, 계획 중인 내용은 별도로 구분합니다.
