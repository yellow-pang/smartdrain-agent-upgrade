# Implementation Workflow

## 1. 사용 조건

다음 작업에서 사용합니다.

- 사용자가 Plans 문서를 승인한 작업
- 작업 범위가 명확한 소규모 수정
- 기존 기능에 대한 버그 수정
- 테스트 추가
- 문서와 구현의 불일치 수정
- 승인된 리팩터링 적용

승인이 필요한 변경이 포함되어 있지만 아직 승인을 받지 못한 경우 구현하지 않습니다.

## 2. 사전 확인

다음을 확인합니다.

```bash
git status --short --branch
```

확인할 내용:

- 올바른 브랜치인지
- 기존 사용자 변경이 무엇인지
- 승인된 Plans 문서의 최신 내용
- 이번 구현 대상 파일
- 실행할 검증 명령

사용자가 Plans 승인 후 파일을 직접 수정했다면 현재 코드와 계획의 차이를 먼저 확인합니다.

## 3. 구현 범위

승인된 Plans의 다음 내용을 기준으로 작업합니다.

- 작업 범위
- 작업 제외 범위
- 수정 예상 파일
- 단계별 작업 계획
- 승인된 기술 선택
- 검증 방법

계획에 없는 변경이 필요해진 경우 임의로 범위를 확대하지 않습니다.

다음 내용을 사용자에게 보고합니다.

- 추가 변경이 필요한 이유
- 대상 파일
- 기존 계획에 미치는 영향
- 호환성 또는 배포 위험

## 4. 구현 원칙

- 기존 프로젝트 패턴을 먼저 재사용합니다.
- 한 번에 너무 많은 파일을 수정하지 않습니다.
- 구조 변경과 동작 변경을 가능한 한 분리합니다.
- 임시 코드와 디버그 로그를 최종 결과에 남기지 않습니다.
- 사용자 변경을 덮어쓰지 않습니다.
- 패키지나 설정 변경은 승인된 범위 안에서만 수행합니다.
- API 계약을 한쪽 서비스에서만 변경하지 않습니다.
- 코드와 문서가 달라지면 관련 문서를 함께 갱신합니다.

## 5. 단계별 구현

복잡한 작업은 Phase별로 진행합니다.

각 Phase에서 다음 순서를 따릅니다.

1. 대상 파일 확인
2. 최소 변경 적용
3. import와 타입 확인
4. 관련 검증 실행
5. Git diff 확인
6. 다음 Phase 진행 가능 여부 판단

이전 Phase에서 중요한 검증이 실패한 상태라면 원인을 확인하기 전 다음 Phase로 진행하지 않습니다.

## 6. 버그 수정

버그 수정 시 다음 순서를 우선합니다.

1. 증상과 재현 조건 확인
2. 관련 데이터 흐름 확인
3. 가능한 원인 비교
4. 가장 가능성 높은 원인을 코드로 확인
5. 가능하면 재현 테스트 추가
6. 최소 범위로 수정
7. 회귀 검증 실행

단순히 오류를 숨기거나 로딩 시간을 늘리는 방식으로 문제를 우회하지 않습니다.

## 7. 서비스별 검증

대상 서비스의 `AGENTS.md`, `docs/reference/verification-guide.md`, 실제 설정을 확인합니다.

Frontend 검증 후보:

```bash
cd frontend
pnpm lint
pnpm exec tsc --noEmit
pnpm build
```

Backend 검증 후보:

```bash
cd backend
python -m pytest
```

AI Service 검증 후보:

```bash
cd ai_service
python -m pytest
```

예시 명령을 무조건 사용하지 않고 실제 `package.json`, 테스트 설정, CI 설정을 우선합니다.

## 8. 계약 변경 검증

API, WebSocket 또는 callback 변경 시 다음을 함께 확인합니다.

- producer
- consumer
- request 타입
- response 타입
- adapter
- 오류 처리
- 문서
- 관련 테스트

한쪽 서비스의 컴파일이나 테스트만 통과했다고 전체 계약이 검증된 것으로 보지 않습니다.

## 9. 검증 실패 처리

검증이 실패하면 다음을 구분합니다.

- 이번 작업으로 발생한 오류
- 작업 전부터 존재한 오류
- 로컬 환경 부족으로 실행하지 못한 검증
- 외부 DB, 네트워크, 모델 파일 의존 오류

검증 실패를 숨기거나 우회 설정을 추가하지 않습니다.

실행하지 못한 검증은 항목과 이유를 최종 보고에 작성합니다.

## 10. 구현 완료 확인

다음을 확인합니다.

```bash
git status --short
git diff
```

확인할 내용:

- 요청 범위 밖 변경 여부
- 디버그 코드
- 임시 파일
- 생성 파일
- 비밀값
- 불필요한 포맷 변경
- 계획과 다른 구현
- 관련 문서 누락

## 11. 최종 보고

다음 형식으로 보고합니다.

1. 변경 목적
2. 구현 결과
3. 주요 변경 파일
4. 파일별 역할
5. 데이터 또는 실행 흐름
6. 수행한 검증
7. 검증 결과
8. 실행하지 못한 검증
9. Plans와 달라진 내용
10. 남은 위험 및 후속 작업

실제 Git 변경이 있다면 이번 작업 변경만 기준으로 한글 Conventional Commit 메시지를 제안합니다.

## 12. 다음 단계

구현과 검증이 완료된 뒤 기록 가치가 있거나 사용자가 요청한 경우 `steps-documentation` Skill을 사용하여 작업 기록을 작성합니다.

오탈자 수정, 한 파일의 작은 문서 교정, 기록 가치가 낮은 매우 작은 변경은 Steps 문서를 생략할 수 있습니다.
