# Task Planning

## 1. 사용 조건

다음 중 하나에 해당하면 이 Skill을 사용합니다.

- 사용자 승인이 필요한 변경
- 여러 파일에 걸친 동작 변경
- 여러 계층 또는 서비스에 걸친 변경
- API 계약 변경
- WebSocket 계약 변경
- AI callback 계약 변경
- DB schema 또는 migration 변경
- Docker, Nginx, CI/CD 변경
- 실행 방식 또는 데이터 흐름 변경
- 구현 방법이 둘 이상인 작업
- 대규모 리팩터링
- 사용자가 계획 문서 작성을 요청한 작업

한 파일의 작은 오류 수정, 오탈자 수정, 문서와 실제 구현의 불일치를 바로잡는 작은 교정처럼 영향 범위가 명확하고 구조나 동작을 바꾸지 않는 작업에는 생략할 수 있습니다.

## 2. Git 및 브랜치 확인

다음을 실행합니다.

```bash
git status --short --branch
git branch --show-current
```

확인할 내용:

- 현재 브랜치
- 기존 미커밋 변경
- 사용자 변경과 이번 작업의 예상 변경 구분
- 현재 브랜치와 요청 목적의 일치 여부

브랜치가 요청 목적과 맞지 않으면 계획 문서를 포함한 파일 변경을 시작하지 않고 적절한 브랜치 이름을 추천합니다.

사용자가 명시적으로 요청하지 않는 한 브랜치를 생성하거나 체크아웃하지 않습니다.

## 3. 현재 구현 조사

관련 영역에서 다음을 확인합니다.

- 디렉터리와 파일 구조
- 실행 진입점
- 관련 코드
- API와 타입
- 환경변수
- 테스트 설정
- Docker 및 CI 설정
- 기존 Plans, Steps, PR 문서
- README 및 아키텍처 문서

문서와 구현이 다르면 실제 실행 가능한 구현을 기준으로 차이를 정리합니다.

추측만으로 계획을 작성하지 않습니다.

## 4. 작업 범위 구분

다음을 명확히 구분합니다.

### 작업 범위

이번 요청에서 실제로 수정할 대상입니다.

### 작업 제외 범위

관련은 있지만 이번 작업에서는 수정하지 않을 대상입니다.

### 승인 필요 범위

사용자 선택이나 승인이 있어야 하는 대상입니다.

### 후속 작업

현재 작업과 섞지 않고 별도 브랜치나 별도 작업으로 분리할 내용입니다.

## 5. 구현 대안 비교

구현 방법이 둘 이상이면 다음 기준으로 비교합니다.

- 현재 구조와의 일관성
- 변경 범위
- 하위 호환성
- 유지보수성
- 테스트 가능성
- 배포 영향
- 장애 위험
- 향후 확장성
- 구현 복잡도

각 대안의 장점과 단점을 작성한 뒤 추천 방향을 하나 명확히 선택합니다.

선택 이유는 현재 코드와 프로젝트 상황에 근거해야 합니다.

## 6. Plans 문서 위치

기존 `plans` 문서가 있으면 다음을 먼저 확인합니다.

- 저장 위치
- 파일명 규칙
- 번호 체계
- 제목 형식
- 섹션 순서
- 문체

기존 규칙이 없으면 다음 경로를 사용합니다.

```text
docs/plans/
```

특정 서비스에만 해당하고 기존 서비스 문서 구조가 있다면 다음 형태를 사용할 수 있습니다.

```text
frontend/docs/plans/
```

현재 저장소에는 `frontend/docs/plans/`가 존재하지만 `backend/docs/plans/`, `ai_service/docs/plans/`는 없습니다. 존재하지 않는 디렉터리를 Plans 작성을 위해 임의로 만들지 말고, 기존 구조가 없으면 `docs/plans/`를 사용합니다.

기본 파일명:

```text
plan-<번호>-<작업명>.md
```

예:

```text
plan-01-frontend-dashboard-refactoring.md
```

## 7. Plans 문서 필수 내용

Plans 문서에는 다음 내용을 포함합니다.

1. 요청 배경
2. 해결하려는 문제
3. 현재 구현 상태
4. 확인한 코드와 문서 근거
5. 작업 범위
6. 작업 제외 범위
7. 구현 대안 비교
8. 추천 구현 방향
9. 선택 이유
10. 수정하거나 추가할 예상 파일
11. 단계별 작업 계획
12. 데이터 또는 실행 흐름
13. 예상 영향
14. 위험 요소
15. 검증 방법
16. 사용자 승인이 필요한 결정 사항
17. 후속 작업

아직 수행하지 않은 작업을 완료된 것처럼 작성하지 않습니다.

## 8. 대규모 변경 계획

대규모 파일 이동이나 구조 변경은 한 번에 수행하지 않습니다.

다음과 같이 Phase를 나눕니다.

```text
Phase 1: 공통 타입 및 인터페이스 정리
Phase 2: 기능 단위 파일 이동
Phase 3: import 경로 수정
Phase 4: 테스트 이동 및 보완
Phase 5: Docker와 CI 경로 갱신
Phase 6: 문서 갱신
```

각 Phase는 가능한 한 독립적으로 검증할 수 있어야 합니다.

파일 이동 계획은 다음 표를 사용할 수 있습니다.

| 현재 경로 | 변경 경로 | 변경 이유 | 영향받는 코드 | 검증 방법 |
| --------- | --------- | --------- | ------------- | --------- |

## 9. 사용자 승인 대기

Plans 문서를 작성한 뒤 실제 구현을 진행하지 않습니다.

사용자가 다음 중 하나를 명시할 때까지 중단합니다.

- 계획 승인
- 특정 대안 선택
- 계획 수정 요청
- 작업 취소

사용자가 계획 수정을 요청하면 Plans 문서를 먼저 갱신하고 다시 승인을 받습니다.

## 10. Git 변경 확인

Plans 문서 작성으로 Git 변경이 발생했다면 다음을 확인합니다.

```bash
git status --short
git diff -- <작성한 Plans 문서>
```

이번 단계에서 작성한 Plans 문서만 기준으로 한글 Conventional Commit 메시지를 제안합니다.

실제 commit은 수행하지 않습니다.
